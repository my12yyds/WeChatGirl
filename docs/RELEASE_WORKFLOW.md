# 打包与发行日志流程

每次准备打包，先核对变更并整理用户可读的日志与验证计划，再构建。发行日志与对应源码提交一起上传，GitHub Release 正文使用同版本的独立日志文件；仅在产品行为或发布范围仍有歧义时再询问确认。

## 打包前

1. 核对工作区、当前版本、最近正式标签和上次发行之后的提交。检查完整差异，不只照搬提交标题。
2. 按“新增、修复、优化、升级注意”整理用户可理解的变更；只写已经实现的内容，注明配置迁移、兼容范围和未完成验证。
3. 创建 `docs/releases/<版本>.md`，并把该版本日志加到 `RELEASE_NOTES.md` 顶部。列出对应测试、手工检查、构建结果和未覆盖范围。
4. 在开始打包前，把该日志摘要与验证计划输出给用户。检查版本号与应用 manifest、插件宿主、安装器一致。
5. 仅运行当前仓库实际存在的打包和验证脚本。若脚本或锁文件缺失，先补齐或明确使用了哪个受控构建环境；不可把不存在的 `npm run` 命令写成已执行。

可用 `node scripts/release-summary.mjs` 查看自最近标签以来的提交标题与变更文件清单。这是日志草稿材料，仍需人工逐项核对实际行为，不能直接当作最终发行说明。

## 打包后

- 用隔离目录验收全新安装、同目录升级、数据保留和卸载路径；不能用真实聊天发送测试消息。
- 检查归档清单，确保不含 `state/`、账号配置、令牌、Cookie、聊天记录、个人插件数据或构建临时文件。核对捆绑插件版本和第三方许可证。
- 记录安装包版本、SHA256、验证环境、验证范围和已知限制。发布日志明确区分自动化验证与真实设备验收。
- 将源码、日志和必要的验证元数据提交并推送；安装器、便携包和校验附件放 GitHub Release，不放进 Git 源码历史。
- 创建与版本匹配的标签和 Release，并以 `docs/releases/<版本>.md` 作为 Release 正文。上传后核对附件名称、大小与 SHA256。

## Windows 发布命令

在已审计的 Windows x64 发行目录上，运行 `scripts/sync-and-package.ps1`。它只向新的隔离暂存目录复制程序与运行资源，以 Git 审核文件集填充源码，重新生成部署清单，再构建便携包、安装器、可选语音 ZIP 和 SHA256。当前脚本不更新活动安装、不复制基线的工作区、账号设置、桌面会话或 state，也不强制退出程序。

首次使用或更换来源时显式传入 `-Version`、`-Baseline`、`-ClientRoot`、`-HookRoot`、`-StagingDirectory` 和 `-OutputDirectory`。客户端 EXE、核心 DLL 与发送组件构建记录需精确匹配 4.1.15.13，并核验腾讯签名、x64 架构、DLL 与加载器哈希，以及语音组件标记；客户端根目录的代理 DLL 和本机令牌不复制。脚本拒绝覆盖已有暂存与输出目录，构建后仍需检查归档与 SHA256。

如果只需从已有 DDF 测量语音拆分效果，可运行：

```powershell
.\scripts\prepare-release.ps1 -DirectiveFile 'D:\发布目录\WeChatGirl.DDF' -PayloadRoot 'D:\发布目录\WeChatGirl' -OutputDirectory 'D:\发布产物\WeChatGirl'
```

此 DDF 脚本只生成核心清单和可选资源 ZIP；它不替代完整安装器生成。正式附件仍须核对归档内容、哈希、构建摘要及隔离目录安装结果。
